# Игровая студия EVOLUTION

Постоянная команда субагентов Codebuff/Freebuff. Определения лежат в `.agents/*.ts`
и используют официальный формат `AgentDefinition` (`id`, `model`, `toolNames`,
`spawnableAgents`, `spawnerPrompt`, `systemPrompt`, `instructionsPrompt`).
Типы для редактора — `.agents/types/agent-definition.ts`.

## Состав команды

| id | Роль | Что делает | Может писать файлы |
| --- | --- | --- | --- |
| `studio-lead` | Руководитель студии | анализ → план → делегирование → интеграция → ревью → отчёт | да |
| `product-owner` | Product owner | ценность для игрока, приоритеты, scope cut | нет |
| `team-manager` | Team manager | декомпозиция, зависимости, владение файлами | нет |
| `technical-director` | Technical direction | архитектура, детерминизм, производительность, риски | нет |
| `engine-programmer` | Engine programming | C#-системы, NUnit-тесты Core, проверки | да |
| `art-director` | Creative direction / technical art | вода, свет, силуэты, URP, визуальные критерии | да |
| `content-designer` | Content / level design | ниши, события, цели, риск/награда, сценарии seed | да |
| `narrative-designer` | Narrative design / writer | хроника линии, вехи, причины смерти, русский текст | да |
| `ux-designer` | UX design | HUD, onboarding, управление, читаемость | да |
| `audio-designer` | Audio | океан, отклики, микс, настоящие Unity AudioClip/AudioSource | да |
| `game-analyst` | Game analytics | баланс, прогрессия, энергетика, прогоны тестов | нет |
| `code-reviewer` | Reviewer | независимый diff-ревью и вердикт PASS/FIX/BLOCKED | нет |
| `devops-engineer` | Devops | CI, GameCI, dotnet/локализация, воспроизводимость | да |

`studio-lead` — единственный агент, который спавнит остальных. Специалисты не
спавнят друг друга, чтобы не плодить вложенные циклы и конфликты владения.

## Правила делегирования

1. **Одна веха — один измеримый результат.** Не запускать следующую, пока текущая
   не интегрирована и не проверена.
2. **Параллельно только независимое.** Одновременный запуск разрешён, если задачи
   не редактируют общие файлы: например `game-analyst` + `product-owner` +
   `technical-director`. Код после архитектурного разбора — последовательно.
3. **Владелец файла один.** Перед параллельным запуском `team-manager` фиксирует
   пути для каждого агента. Пересечение запрещено; связующие правки делает
   `studio-lead`.
4. **Результат, а не роль.** Каждый агент обязан вернуть артефакт: diff, тест,
   отчёт с путями и числами, вердикт. Общие слова без доказательств возвращаются
   на доработку один раз.
5. **Ревью независимо.** `code-reviewer` не редактирует код и не доверяет отчёту
   автора. Веха с критическими замечаниями не принимается.
6. **Никаких фиктивных проверок.** Нет Unity Editor — отдельно указывать
   статические проверки и неподтверждённый импорт/рендер. Нет скриншота — писать
   «не viewed», а не «выглядит хорошо».
7. **Инварианты проекта.** Unity 6000.6.9f1; `"com.unity.modules.audio": "1.0.0"`
   в `Packages/manifest.json`; настоящие Unity `AudioClip`/`AudioSource`/
   `AudioListener`; русский по умолчанию; этапы A–G не ломать; auto-merge не
   выполнять.

## Как запускать

В сессии, где `.agents` уже загружены:

```
spawn_agents({ agents: [
  { agent_type: "studio-lead", prompt: "Веха: … Критерий готовности: …" }
]})
```

Один агент напрямую:

```
spawn_agents({ agents: [
  { agent_type: "game-analyst", prompt: "Проверь баланс деления на seed 42…" }
]})
```

`studio-lead` сам вызывает `team-manager` для плана, затем специалистов, затем
`code-reviewer` для приёмки.

## Новая сессия Freebuff Cloud

Реестр агентов читается один раз при старте сессии. Поэтому после слияния PR
нужен **новый Cloud-чат на репозитории**, а не продолжение текущего: каждый
Cloud-чат работает на собственной копии проекта.

1. Убедиться, что PR с `.agents/` слит в `main`.
2. **New chat → Select GitHub repository → Evolution → ветка `main` → Use
   repository** (не «Continue in Cloud» из старого чата — он копирует старый
   снимок без новых файлов).
3. Отправить первое сообщение и дождаться загрузки. Если Codebuff спросит о
   доверии к `.agents/`, разрешить только после просмотра diff этого PR.
4. Проверить именно своих агентов, не `researcher-web`:

```
spawn_agents({ agents: [
  { agent_type: "studio-lead", prompt: "Проверь готовность команды: не меняй файлы. Делегируй трём специалистам параллельно аудит онбординга новичка в CellPrototype и 3D-режиме: product-owner — первые 60 секунд и причина продолжать; ux-designer — конкретные проблемы HUD и управления; game-analyst — реальные числа энергии/деления и риски баланса. Каждый должен вернуть артефакт с путями к файлам. Сведи результаты и укажи, какие проверки не выполнялись." }
]})
```

Внутри `studio-lead` должны параллельно отработать минимум три **локальных**
агента (`product-owner`, `ux-designer`, `game-analyst`) и вернуть конкретные
находки. Если `studio-lead` недоступен, это означает, что реестр не загрузил
каталог: не подменять команду `researcher-web`, а проверить наличие `.agents/`
в копии сессии, trust-gate и перезапустить новый чат.

## Проверка команды

Выполнено в облачной среде 2026-11-24:

- 13 файлов агентов импортированы Bun как TypeScript-модули: **13/13**, без
  дубликатов `id`, неизвестных `toolNames` и битых ссылок `spawnableAgents`.
- `python3 -B Tools/check_studio_agents.py` проверяет те же инварианты в CI
  (`core-tests.yml`) без исполнения TypeScript.
- `studio-lead` ссылается на 12 локальных агентов, все найдены.
- Структурная проверка не заменяет запуск в новой сессии: реестр агентов
  Freebuff строится при старте, поэтому файлы, созданные в текущей сессии, не
  появляются в ней на лету (проверено: спавн `game-analyst` вернул «not
  available»).
- Репозиторные `.agents` в Codebuff проходят trust-gate, так как выполняют
  авторский код. В новой сессии нужно подтвердить, что каталог доверен; если
  Freebuff Cloud его пропускает, команда недоступна, и это нужно указать явно,
  а не имитировать вызовы.
- В текущей сессии реально доступен только `researcher-web`; четыре его
  независимых вызова выполнены параллельно (product, URP-арт, UX, audio).

## Внешние ориентиры первой итерации

Материалы, собранные исследовательскими субагентами; это дизайн-выводы, а не
доказанные метрики удержания.

- **Прогрессия.** Быстрое действие с видимой наградой, затем рост, меняющий
  возможности (редактор/органоиды), тактический выбор пищи и конкретная
  следующая цель. Spore: руководство Cell Stage; Thrive: Microbe Stage GDD.
- **Визуал URP.** Полноэкранное поглощение по глубине, каустики в материалах,
  несколько геометрических лучей; ray marching — только по бюджету. Готовой
  URP-системы каустик/volumetric fog нет, документация Unity в основном HDRP.
- **UX.** Progressive disclosure, контекстные подсказки у элемента, одна
  следующая цель, визуальное выделение изменения и цепочка «действие → эффект →
  цена».
- **Аудио.** Слоистый loop-ambience, разделение 2D-фона и 3D-событий, небольшой
  разброс pitch между короткими звуками, пул `AudioSource`, приоритеты и группы
  Audio Mixer, один `AudioListener`.

Ссылки на источники сохранены в отчёте исследовательских вызовов; при переносе
решений в код проверять актуальность документации Unity 6.6.
