# EVOLUTION Autopilot — план безопасной ночной разработки

## Цель
Последовательные автономные циклы: выбор задачи → реализация → GitHub CI/Unity Visual Preview → анализ кода и настоящих кадров → доработка или следующая задача. Утром — сводка изменений и ссылки.

## Правила автономного цикла
- Работать в новых ветках/draft PR, **никогда не auto-merge в main**.
- Каждая итерация — одна ограниченная функциональная задача + тесты. Не изменять огромные подсистемы одновременно.
- Перед новой задачей проверять последний draft PR, CI, реальные изображения и связанные ошибки. При провале — исправить текущую ветку, не переходить к следующему этапу.
- Опираться только на фактически прошедшие тесты и существующие изображения. Указывать head SHA, UTC timestamp, ссылки на run/artifacts.
- Визуальный агент-рецензент должен сравнивать новые изображения с предыдущими и пользовательским референсом; не объявлять успешный рендер по зелёному select-job без render/artifact.
- Два неудачных исправления подряд — остановка и отчёт, а не бесконечный цикл.
- Ночной лимит по умолчанию для будущего автономного исполнителя: до 4 итераций, до 2 исправлений на задачу; ограничивать минуты CI и бюджет API отдельно.
- Не публиковать лицензии Unity, токены, raw logs или сведения, позволяющие их восстановить.
- Ограничить параллелизм и предотвращать конфликты Git-веток.
- Unity 6000.6.9f1, URP, `com.unity.modules.audio` = `1.0.0`; не удалять предыдущие механики.
- Никаких фиктивных кадров, игровых состояний, тестов или «успехов».
- Итог за ночь: PR и SHA, что пользователь теперь может делать, результаты Core/Unity/Visual Preview, ссылки на кадры, оставшиеся ошибки и следующая задача.

## Что ещё НЕ настроено
Это документ управления процессом, а не запущенный агент. Для запуска нескольких циклов без ПК необходим поддерживаемый механизм автоматического старта Codex Cloud или внешний оркестратор с допустимой авторизацией и бюджетом. GitHub Actions и ChatGPT scheduled tasks сами по себе не гарантируют запуск новой облачной задачи Codex. Не внедрять платный API и не запрашивать секреты без отдельного согласования.

## Обязательный цикл независимого ревью (после КАЖДОГО изменения)

Роль независимого проверяющего выполняется отдельным аналитическим шагом агента, даже если тот же агент писал код.

1. **Изучить код:** реальный diff, изменения игровой логики, обратную совместимость, тесты и риски.
2. **Получить доказательства:** проверить GitHub CI и статус render job, открыть настоящие кадры из Visual Preview, сравнить с предыдущим успешным кадром и референсом. Если изображение не удалось прочитать, написать это прямо.
3. **Оценить игровой результат:** состояние воды и глубины, внешний вид клеток, HUD, управление, стратегический обзор, производительность, достоверность выводимых показателей.
4. **Поставить вердикт:** `PASS` — всё доступное проверено, можно выбирать следующую задачу; `FIX` — есть конкретные ошибки/недоработки, сначала исправить; `BLOCKED` — нет достаточных доказательств, не объявлять успех.
5. **Принять решение:** описать почему исправлять или какую новую задачу брать. Учитывать пользовательский приоритет (живой, красивый, удобный 3D-микромир с полноценной эволюцией), а не количество строк/коммитов.
6. **Повторить проверку** после исправлений; зафиксировать в отчёте ссылку на PR, точный SHA, запуск Actions, кадры, недостатки и следующее решение.

Обязательный формат вывода каждой итерации:
```
Результат: PASS / FIX / BLOCKED
PR/SHA:
Код и тесты (что реально прошло):
Unity/скриншоты (что реально видел):
Проблемы и приоритет:
Решение (почему):
Следующее действие:
```

Ни новый PR, ни зелёный GitHub select-job сами по себе не являются одобрением. Если проверка требует пользователя, отправить понятный запрос и продолжать только независимые задачи до получения данных.
